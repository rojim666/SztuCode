# 资料库变更流程

所有远端资料库变更都先解析**实际写入目标**的空间类型。用户的原始明确请求直接授权我的文档（`category=personal`）中操作对象与范围均已明确的变更；只有任一实际写入目标属于团队空间（`category=team`）时，才展示最终方案并停下来等待用户确认。

## 目标分类

- 操作已有节点：先用 `space.workspace.node-info` 取得实际 `spaceId`，再与 `space.workspace.list-user-spaces` 返回的同一 `spaceId` 精确匹配，以其 `category` 为准。
- 用户显式指定空间或目录：按该空间的实际 `spaceId` 和 `category`；指定 `parentId` 时先解析父节点所属空间并校验一致。
- 没有显式目标：创建、导入或上传时省略可选 `spaceId`，后端默认目标按 `personal` 处理。
- `space.workspace.create-space` 创建结果固定为 `team`，所以调用创建接口前须走团队空间确认。
- 一个不可分割的方案写入多个资源时，只要其中一个实际目标是 `team`，整条提交链路按团队空间处理并只确认一次。

用户显式指定我的文档或已有我的文档节点时，按其实际 `category` 走我的文档分支；写入显式团队空间时走团队分支。空间类型缺失、不是 `personal` / `team`、无法与 `spaceId` 唯一匹配或上下文互相矛盾时停止提交，先解析或消歧，不得默认当作我的文档。

## 执行

1. 定位节点、类型、当前位置和目标目录；新建或上传也要解析出明确目标。
2. 确认正式 Agent 能力已开放；未开放则直接拒绝，不试探调用。
3. 按上节确定每个实际写入目标的空间类型并校验当前角色可写；`reader/invalid` 或其它不可写信号直接拒绝，不先向用户请求确认。
4. 读取最新内容、节点、目标目录和同级节点状态，建立基线并完成同名检查。
5. 分支执行：
   - 仅含 `personal` 目标：原始请求已构成提交授权。紧邻提交前复查基线和权限；目标、范围及用户可见结果仍与原始请求一致时，直接按对应模块的原生路径提交。
   - 含 `team` 目标：按“团队空间确认”展示最终方案并停止。只有用户在展示后明确同意该方案，才复查基线和权限并提交；任一确认项或远端基线变化时，旧确认失效，重新展示并等待确认。
6. 提交后只读验收；结果不明时先查询，不盲目重试。

我的文档目标复查时若远端基线变化，但仍能在最新基线上唯一实现用户原本要求，可重建变更后直接继续；若变化导致目标不唯一、语义改变、影响范围扩大或无法证明结果等价，则先向用户说明并消歧。用户未明确要求的删除、覆盖、字段类型转换等额外动作也属于范围扩大，不能自行执行。

静默执行本流程。模块中的“直接写入”“无需审阅”或“不询问技术路径”只选择原生提交路径；团队目标仍须确认。Doc 审阅卡虽由产品内的接受/拒绝决定正文是否生效，但提交审阅卡本身仍按实际目标空间分类。

本规则只取消我的文档的通用 mutation 二次授权；目标消歧、用户未授权的额外范围、产品形态或 Schema 选择，以及已发布 Page 的独立发布态同步，仍按对应模块规则处理。

## 团队空间确认

确认时直接说明将做什么、在哪里做以及用户可见的变化，并用一两句话自然询问；内容复杂时再使用简短列表或 diff，不默认使用标题或表格。确认前不得发送业务写调用，也不得申请上传凭证、PUT 文件或发起导入。

运行环境仅用于内部路由和鉴权；除非用户明确询问，不向用户输出。在对用户可见的思考、过程说明和回复中，不引用本文件、流程、规则、章节、步骤或授权状态。角色、权限、内部 ID、基线标识或策略枚举仅在消歧、风险说明或排错确有必要时提供。

- 创建 / 上传：文件或产物、最终名称和目标目录。
- 修改 / 内容删除：目标和修改结果；文本展示 diff，Database 展示字段/记录 before → after，Page 或二进制文件展示结构化摘要及可核对预览。
- 移动：源节点、原位置和目标目录。
- 重命名：原名称和最终新名称。
- 删除、覆盖、字段类型转换或删除字段选项等可能不可逆、清空数据的动作：明确说明对应风险。

确认只对已展示的操作、目标、内容、位置、名称和影响有效。完整展示影响后，不可分割的多调用提交链路可共用一次确认。

## 同名与覆盖

- 无冲突时，不向用户提及同名检查或处理方式。
- 团队目标发现冲突时，把同名事实和影响并入最终确认，只询问是否仍执行用户原本要求的结果；不列处理选项，不主动建议其它名称。
- 我的文档目标的新建、上传、移动或重命名已经由用户明确给出最终名称和唯一目标时，即使存在同名节点也按原名直接执行；不得静默改名或覆盖。
- 多个同名候选导致已有操作目标不唯一时，先让用户消歧；这是目标选择，不是 mutation 二次确认。
- 仅当用户主动要求自动改名或覆盖时才进入对应分支：自动改名先生成最终名称；覆盖仅在原生接口可原子覆盖明确节点时继续，不得用先删后建模拟。团队目标仍把最终名称或覆盖影响纳入确认。

创建/上传、移动和重命名接口没有通用原子同名处理；提交前后复查同级节点，但不得承诺消除并发冲突。

## 当前不支持

- 文件/文件夹节点删除没有正式 Agent API；Doc block、Database 字段/记录或 Page DOM 删除按“修改”执行。
- 没有历史版本列表或恢复 API；已知 Page 版本号时，只能用 `list_page_artifacts.py --version` 只读获取产物。

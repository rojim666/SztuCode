# Critic-Generator Engine（对抗生成引擎）

> 本引擎定义 Agent 在"**质量审查 + 改进指令生成**"阶段的**标准对抗环路**。对给定文本执行 **"信息隔离 → 加载尺规 → 量化评分 → 强制否定 → 决策 → 报告"** 6 步状态机，输出评分和改进指令。
>
> 本引擎是所有 Expert 共享的 Core 能力。Expert 的 Workflow 在需要做对抗审查时，按本协议执行。**具体参数如何配置，见同目录 `README.md`**。

---

## 一、引擎定位

### 1.1 解决什么问题

AI 自我审查常见的三种失败模式：

1. **作者即审稿人**：模型在生成时已"认定"自己的输出合理，紧接着的自检会倾向于**合理化自己的输出**
2. **一审就通过**：缺乏强约束时，模型倾向于输出"整体不错""基本满足"这类模糊肯定，无法暴露真实问题
3. **建议模糊**：审查意见浮于"建议完善""可以更好"，无可执行的修改方向

本引擎通过三重机制解决：

| 机制 | 解决哪个失败 |
| --- | --- |
| **① Isolate 信息隔离** | 切断推理链惯性 → 解决"作者即审稿人" |
| **④ Challenge 强制否定配额** | 至少 N 项扣分、至少 M 条改进指令 → 解决"一审就通过" |
| **④ Challenge 指令标准化** | 每条指令含 `定位 / 问题 / 严重度 / 修改方向` → 解决"建议模糊" |

### 1.2 适用场景

Expert 的 Workflow 中任何需要"**对已有内容做对抗审查**"的阶段都应调用本引擎，典型场景包括：

- **章节级审查**（scope=`section`）：长文档每写完一章立即审查
- **全文审查**（scope=`full`）：全文写完后的最终验收
- **重写验收**（scope=`revision`）：针对前一轮 P0 扣分点的定向复审

### 1.3 产出物

- **评审报告**：Markdown 文件，包含评分表 + 改进指令清单 + 决策结论
- **决策信号**：`PASS` / `REVISE` / `DEGRADED`，指示调用方（Expert）下一步动作

### 1.4 引擎不负责的事

本引擎**只产出评审意见**，以下职责属于调用方（Expert）：

- ❌ 不执行重写（REVISE 决策由 Expert 接手，决定重写哪部分、怎么重写）
- ❌ 不决定评分维度（由 `rubrics_files` 注入，Engine 不硬编码 7 维或任何维度）
- ❌ 不决定触发时机（每章审 or 全文审由 Expert 的 workflow 决定，通过 `scope` 参数表达）
- ❌ 不生成初稿（初稿生成属于 Expert 的写作阶段）

## 三、六步详细规则

### 3.1 Step ① Isolate（信息隔离）

**目标**：切断推理链惯性，让审查视角**只看产物本身**，不看"为什么这样写"。

**执行规范**：构造一个"盲审包"作为 ② 之后所有步骤的**唯一输入**。盲审包必须**只包含**：

```yaml
盲审包:
  - 待审文本: <草稿全文或章节文本>
  - 审查范围: <scope=section 时的章节标识；scope=full 时为"全文">
  - 需求画像: <文档类型 / 受众层级 / 语体风格 / 行业领域 / 规模>
  - 可查证素材: <Phase 2 搜索结果的标题+来源+Tier，不含搜索过程的决策推理>
  - 前轮扣分指令: <仅 scope=revision 时存在>
```

**强约束**：
- ❌ 禁止在 ② 之后"回忆"生成过程的思考，为当前内容辩护
- ❌ 禁止引用生成时的上下文判断（如"因为用户说了 X，所以这样写合理"）
- ✅ 只能基于**待审文本 + rubrics + 可查证素材**做判定

> **为什么这步关键**：模型生成完内容后，推理链里已经"认定"了合理性。如果不隔离，后续评分会不自觉地合理化自己。信息隔离是把"作者上下文"从审稿视角里物理剥离。

### 3.2 Step ② LoadRubrics（渐进式加载尺规）

**目标**：在审查开始前加载评判标准，**但不在生成阶段加载**。

**执行规范**：
- 按 `rubrics_files` 参数依次调用 `read_file` 加载每个尺规文件
- 加载失败必须抛错跳出（`status=FAILED`），**不得跳过尺规凭记忆审查**
- 每个尺规文件**独立加载记录**（便于 Expert 诊断是哪份尺规缺失）

**为什么要"渐进式"**：
- 若在写作时就加载几万字 rubrics，会让模型的创作注意力被规则淹没，初稿质量反而下降
- 把 rubrics 延迟到审查时才加载，生成阶段纯净、审查阶段严苛

**禁止**：
- ❌ 在 ② 之前让生成者看到 rubrics（由 Expert 的 workflow 保证）
- ❌ 在 ② 之后跳过加载动作（即使模型声称"已熟悉规则"）

### 3.3 Step ③ Score（量化评分）

**目标**：按 rubrics 中定义的维度**逐项量化打分**，禁止模糊判定。

**执行规范**：
- 评分维度由 `rubrics_files` 中的文件定义，**本引擎不硬编码任何维度**
- 每个维度必须输出：**分数 + 扣分证据**（具体段落 / 原文片段）
- 禁止使用"基本满足""整体不错""大体合格"等模糊肯定
- 评分等于满分时，必须附带"**为什么满分**"的具体证据（防止惯性给高分）
- 评分总分按 rubrics 中定义的权重计算（若未定义权重，默认等权平均）

**输出结构**：

```yaml
score_table:
  - dimension: "<维度名，来自 rubrics>"
    score: <数字，范围由 rubrics 定义>
    evidence: "<扣分证据 或 满分证据>"
  - dimension: "..."
    ...
total_score: <按权重计算的综合分>
```

### 3.4 Step ④ Challenge（强制否定 + 指令生成）

**目标**：**强制否定配额** + **标准化改进指令**，防止"一审就通过"。

#### 3.4.1 强制否定配额

| 约束 | 规则 |
| --- | --- |
| 扣分维度下限 | 至少 `min_issues` 个维度评分 ≤ `pass_score`（即未满分维度数 ≥ min_issues） |
| 改进指令下限 | 必须输出至少 `min_instructions` 条具体改进指令 |
| 配额不足时 | 下沉到段落级检查，找最弱的段落生成指令（禁止输出"全部通过"） |

> Expert 通过 `README.md` 配置 `min_issues` / `min_instructions` / `pass_score`，不同 scope 下配额值可以不同（见 README.md §场景模板）。

#### 3.4.2 改进指令标准格式

每条改进指令必须包含 4 个要素：

```yaml
instruction:
  id: "<序号，如 INS-001>"
  location: "<定位：章节/段落/原文片段前 10 字>"
  problem: "<问题描述，≤ 30 字>"
  severity: "P0 | P1 | P2"
  direction: "<具体修改方向，禁止空话>"
```

**严重度定义**：

| 级别 | 定义 | 示例 |
| --- | --- | --- |
| **P0** | 必须修复 | 数据引用错误、违反硬性规则、核心结论缺失 |
| **P1** | 建议修复 | 表达不够清晰、术语不统一、论证不充分 |
| **P2** | 可选优化 | 措辞润色、风格微调、增加锦上添花的素材 |

**修改方向质量标准**：

| ❌ 低质量（禁止） | ✅ 高质量（要求） |
| --- | --- |
| "改好一点" | "用 Phase 2 搜索结果 #3 的 IDC 2024 年数据替换当前虚构的 500 亿数字" |
| "建议完善" | "补充 Q3 维度分析，至少包含 2 段：① 数据陈述 ② 因果推导" |
| "语气再正式" | "把第 2 段'感觉不错'改为'数据表明该趋势稳健'" |

### 3.5 Step ⑤ Decide（决策分支）

**决策矩阵**：

| 当前状态 | 决策 | 调用方动作 |
| --- | --- | --- |
| 存在 ≥1 条 P0 指令 AND `loop_index < max_loops` | `REVISE` | Expert 接收指令 → 重写 → 重新调用本引擎（loop+1） |
| 仅 P1/P2 指令（无 P0） | `PASS` | Expert 进入下一阶段（可选择就地消化 P1 指令） |
| 存在 P0 指令 AND `loop_index ≥ max_loops` | `DEGRADED` | Expert 带未解决 P0 标注强制交付，建议人工审查 |

**关键约束**：
- 本引擎**不执行重写**。REVISE 决策只是返回信号 + 指令清单给调用方
- Expert 重写完后**重新调用本引擎**是一次新的执行（输入是新草稿 + 上一轮的 P0 指令清单），`loop_index` 由调用方维护并传入

### 3.6 Step ⑥ Report（评审报告生成）

**目标**：产出一份结构化的评审报告，供 Expert 消费。

**报告标准结构**（Markdown）：

```markdown
# Critic 评审报告：{title or chapter}

## 元数据
- **审查范围**: section | full | revision
- **本轮 loop_index**: {N}
- **决策**: PASS | REVISE | DEGRADED

## 评分表
| 维度 | 分数 | 扣分证据 |
| --- | --- | --- |
| {dim_1} | {score} | ... |
| ... | ... | ... |
| **综合分** | {total} | — |

## 改进指令
### INS-001  [P0]
- **定位**: 第 3 章第 2 段 "2025年市场规模..."
- **问题**: 数字无来源，疑似虚构
- **修改方向**: 用 Phase 2 搜索结果 #3 的 IDC 2024 数据替换

### INS-002  [P1]
...

## 决策说明
{PASS / REVISE / DEGRADED 的具体原因}

## 未解决项（仅 DEGRADED 时）
- ⚠️ INS-001（P0）经 2 轮重写仍未达标，建议人工审查
```

**落盘路径**：由 Expert 通过参数 `report_path` 指定，本引擎不硬编码。

## 四、引擎契约

本引擎对所有调用方（Expert Workflow）承诺：

1. **只跑 6 步状态机**，不执行重写、不选择评分维度、不决定触发时机
2. **Isolate 环节不可跳过**：强制切断推理链惯性
3. **LoadRubrics 环节不可跳过**：尺规加载失败立即抛错，禁止凭记忆审查
4. **Challenge 强制否定配额不可降**：配额不足时下沉到段落级检查，禁止"全部通过"
5. **改进指令 4 要素不可缺**：`location / problem / severity / direction` 缺一不可
6. **决策返回三态**：`PASS` / `REVISE` / `DEGRADED`，由调用方消化
7. **失败不阻塞主流程**：达 `max_loops` 仍有 P0 时降级输出 `DEGRADED` 报告

> 调用本引擎所需的**参数**、**场景模板**、**rubrics 文件要求**见同目录 `README.md`。

## 五、禁止事项

- ❌ 禁止在 ② 之前让生成者看到 rubrics（Expert 的 workflow 负责保证）
- ❌ 禁止跳过 ① Isolate 直接进入评分（会让审查合理化生成过程）
- ❌ 禁止跳过 ② LoadRubrics 凭记忆审查（即使模型声称"已熟悉规则"）
- ❌ 禁止输出"全部通过"（违反 Challenge 强制否定配额）
- ❌ 禁止使用模糊肯定表述（"基本满足""整体不错""大体合格"）
- ❌ 禁止输出无 `direction` 的改进指令（"建议完善"这类空话）
- ❌ 禁止引擎内部执行重写（REVISE 决策返回给调用方，由 Expert 重写后重新调用）
- ❌ 禁止在单次调用内无限循环（loop 由调用方维护并传入）

## 六、失败降级

### 6.1 达 `max_loops` 仍有 P0
1. 进入 ⑥ Report 但在决策区标记 `DEGRADED`
2. 在"未解决项"章节列出所有仍存在的 P0 指令
3. 返回给 Expert，Expert 在最终交付时必须显式标注"本稿经 N 轮重写仍存在 P0 问题，建议人工审查"

### 6.2 rubrics_files 加载失败
1. 立即中断状态机
2. 返回 `FAILED` 状态 + 错误现场（哪份 rubrics 加载失败）
3. **不降级到"凭记忆审查"**，Expert 必须修正 rubrics 路径后重试

### 6.3 Challenge 配额无法满足
1. 强制下沉到段落级检查
2. 从最弱的 2-3 个段落中生成指令
3. 若仍不足，报告中显式标注"本文档质量较高，已下沉段落级审查，最终指令数：{N}（低于配额 {M}）"

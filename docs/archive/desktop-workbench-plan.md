# SztuCode 客户端 Codex 化优化方案

> [!WARNING]
> 这是桌面工作台落地前的历史方案，其中部分技术选型和现状描述已经过时。当前桌面端使用 Tauri 2 + Vue 3；现行架构见 [架构说明](../reference/architecture.md)。

## 1. 结论与目标

SztuCode 已经具备 Agent 产品的核心能力：daemon 与客户端分离、会话持久化、工具调用与权限策略、实时事件流、上下文压缩、Skills、子 Agent 和 MCP。当前短板不在 Agent 内核，而在桌面端没有把这些能力组织成一个开发者可以长期使用的工作台。

本方案的目标是将 `sztu-desktop` 从“单轮聊天窗口”升级为 **本地优先的 Agent 工作台**：用户围绕一个代码仓库创建、恢复和管理任务；在同一界面完成对话、计划、文件变更审阅、终端/工具观察、权限决策与结果验收。产品形态参考 Codex 的效率与信息密度，不复制其品牌、文案或像素级界面。

### 成功定义

1. 用户在 10 秒内可选定工作区并发起任务；中断后可恢复原会话。
2. Agent 的计划、执行、文件变更、权限请求和最终结果都有可追溯的视觉位置。
3. 用户无需离开客户端即可审查 diff、批准高风险操作、撤销未应用改动、打开相关文件。
4. 相同任务在窄屏、普通笔记本屏幕和宽屏上都保持清晰的主次关系。
5. 所有界面状态可由 IPC 事件重建；刷新、断线重连和重放不会产生重复或错位的信息。

## 2. 现状审计

### 已有可复用能力

| 能力 | 已有基础 | 客户端应呈现的产品价值 |
| --- | --- | --- |
| 会话 | `session.create/send_message/get_history/close` 与本地持久化 | 历史任务、恢复、标题、搜索、归档 |
| 事件流 | `run.*`、`tool.*`、`llm.*`、`permission.*`、`context.*`、`subagent.*` | 实时活动流、状态、运行回放 |
| 安全 | 权限模式与逐次决策 | 分级审批、风险说明、可撤销策略 |
| 执行 | 任务、工具、Skills、子 Agent、MCP | 计划、执行树、工具日志与成果 |
| 可观测性 | trace 和事件回放 | 运行诊断、问题复盘、性能与成本分析 |

### 当前客户端问题

1. `src/sztu_code/desktop/app.py` 是一个 28KB 的 Tkinter 单窗口，只有顶部状态、聊天流和输入框；没有工作区、任务列表、文件树、diff、设置或恢复会话入口。
2. Tkinter 结构把布局、状态、事件订阅和渲染放在同一类中，难以实现虚拟列表、可停靠面板、复杂键盘导航和高质量代码 diff。
3. 桌面端 IPC 名称已漂移：它监听 `tool.started/tool.finished`，但核心事件为 `tool.call_started/tool.call_finished`；它调用 `permission.decide`，而 daemon 注册的是 `permission.respond`。这属于 P0 正确性问题，必须先修复。
4. 现有协议可获取单个会话历史，但没有会话列表、重命名、归档、恢复、工作区、文件变更、运行取消等面向产品的命令。
5. 目前的模式按钮使用字母缩写，权限弹窗只给“批准/拒绝”，无法解释影响范围，也无法表达“一次允许/始终允许”等已有后端能力。

## 3. 产品定位与设计原则

### 产品定位

**SztuCode 是一个本地代码仓库的 Agent 协作桌面端。** 它不是聊天机器人，也不是 IDE 替代品：它应成为“任务的控制台”，并能与用户已有编辑器协同。

### 设计原则

- **任务优先**：默认视图回答“Agent 正在为哪个仓库做什么、进行到哪一步、产生了哪些改动”。
- **渐进披露**：普通对话只显示结论与当前行动；工具参数、原始输出、trace 按需展开。
- **可控自治**：模式是易读的策略选择，不以模糊缩写表达；任何会改变外部状态的动作都给出范围、命令和风险。
- **本地优先与可恢复**：界面重启或连接中断后，可恢复任务、消息、计划和事件时间线。
- **开发者密度**：深色、紧凑、等宽代码区、明确状态色；避免把每条 Agent 输出都做成气泡。
- **键盘优先，鼠标完整可用**：命令面板、全局快捷键、焦点顺序与可见的快捷键提示同时提供。

### 视觉方向

采用“**精密的深色工程台**”而非通用聊天产品：近黑蓝灰作为大面积背景，暖白文字保证长时间阅读，青绿色仅用于已完成/可安全执行，琥珀色用于待确认，红色只用于阻断与失败。主内容弱卡片化，靠分隔线、留白和层级建立结构；代码与数据使用等宽字体，叙述使用中文可读性更好的无衬线字体。

```text
圆角：6px（控件）/ 10px（面板）  间距基准：4px
```

## 5. 主界面与关键交互

### 5.1 默认三栏布局

```text
┌──────────┬──────────────────────────────────────────┬──────────────────────┐
│ 工作区   │ repo / branch · 当前任务标题 · 运行状态     │ 任务上下文           │
│ + 新任务 ├──────────────────────────────────────────┤ 计划 3/5            │
│ 搜索…    │                                          │ 子 Agent / 工具      │
│          │  用户目标                                 │ 待审批（如有）       │
│ 今天     │  Agent 结论 / 进度 / 折叠的执行卡          │                      │
│ · 修复…  │                                          ├──────────────────────┤
│ · 代码…  │  [输入任务…               ] [模式] [发送] │ 变更 3 个文件        │
│          │                                          │ 通过 12 / 12 tests   │
└──────────┴──────────────────────────────────────────┴──────────────────────┘
```

- 左栏宽 264px：工作区切换、新任务、搜索、按“今天/本周/更早”分组的会话。悬停显示重命名、固定、归档；运行中任务有脉冲状态点。
- 中栏是唯一的主要阅读流：用户目标、Agent 叙述、计划卡、执行卡、审批卡和最终交付。工具原始输出默认折叠。
- 右栏宽 320px，可收起：上半区显示计划/子 Agent/待办，下半区显示 Git 变更和测试状态；点击任一项在中栏或底部检查器定位。
- 窄屏时左栏变为抽屉、右栏变为底部 sheet；主对话永远保留。

### 5.2 启动与空状态

首次进入先显示工作区选择，而不是空聊天框：最近仓库、打开本地文件夹、克隆仓库、演示任务四种入口。选择后显示“你想完成什么？”和三条与代码仓库相关的示例任务。若 daemon 未启动，显示明确的连接状态及“启动本地服务/重试/查看诊断”操作，不能静默禁用输入。

### 5.3 任务生命周期

1. 用户输入目标，可用 `@文件`、`#Skill`、拖入文件、粘贴图片/日志作为上下文。
2. 发送前选择模式：**计划**、**建议修改**、**自动执行**。模式旁展示一句话风险说明。
3. Agent 创建计划；用户可确认、编辑、跳过或要求拆分。自动执行模式可直接开始，但仍保留停止按钮。
4. 执行时，中栏显示当前一步和可折叠时间线；右栏实时更新文件、测试、子 Agent 与 token 预算。
5. 完成时输出统一交付卡：完成摘要、变更文件、验证结果、风险/未完成项、可复制的下一步；提供“查看 diff”“继续追问”“新建关联任务”。

### 5.4 输入框与命令面板

- 输入框支持多行、附件、`@` 文件引用、`/` 命令和语音/截图入口（后两项可排入后续版本）。
- 发送按钮在运行时变为“停止”，仍可排队下一条消息；按 `Ctrl+Enter` 发送，`Enter` 换行可在设置中切换。
- `Ctrl+K` 打开命令面板：新任务、切换工作区、切换模式、紧凑上下文、打开设置、查看变更、运行测试、恢复最近任务。
- `Ctrl+1/2/3` 聚焦左栏/主栏/右栏；`Ctrl+Shift+P` 进入计划模式；`Esc` 关闭面板或停止流式输出确认。

### 5.5 计划、执行与子 Agent

- 计划卡是可勾选的 3–8 项列表，状态为“待开始 / 进行中 / 已完成 / 阻塞”。点击可看到该步产物和关联工具调用。
- 每个子 Agent 显示任务名、父任务、耗时、状态与最终结论；默认只显示摘要，避免并发日志淹没主流。
- 工具卡区分读取、修改、命令、网络、MCP；显示人类可读摘要、目标文件/命令、耗时、退出状态，失败时给出“重试 / 查看详情 / 引导 Agent 修复”。

### 5.6 文件变更与审阅

右栏“变更”常驻显示：新增、修改、删除文件数及测试结果。打开后进入底部检查器或独立 diff 标签页：

- 文件列表带增删行数、语言图标和未读标记。
- 默认 split diff；窄屏改 unified diff；支持忽略空白、词级 diff、复制 hunk、跳转外部编辑器。
- 每个文件可写审阅评论并“一键让 Agent 修复”。
- 仅对 Agent 本轮工作目录中的未提交改动提供“撤销本次改动”，操作前列出准确文件和 diff；Git 提交、推送、删除等危险动作必须单独确认。

### 5.7 权限与安全

权限请求采用非阻塞的底部审批条，而非遮挡内容的普通弹窗。卡片必须展示：动作类型、影响范围、精确命令/路径、为什么需要、风险等级、可展开的完整参数。

按钮按策略映射已有后端决策：

| 动作 | 可选决策 |
| --- | --- |
| 只读文件/目录 | 允许一次、始终允许、拒绝 |
| 编辑文件 | 允许本次任务、始终允许此工作区、拒绝 |
| shell / 网络 / Git 写操作 | 允许一次、拒绝；高风险额外输入确认 |

“自动执行”不是绕过安全，而是默认允许低风险规则；状态栏始终可见当前权限策略。所有决策写入任务时间线并可以在设置中撤销“始终允许”。

## 6. 功能路线与协议改造

### P0：先恢复桌面端正确性（必须）

1. 对齐桌面端事件名：`tool.call_started`、`tool.call_finished`、`tool.call_failed`、`run.finished(status)`、`context.compacted`、`log.line`。
2. 对齐审批调用：使用 `permission.respond`，并传递 `allow_once / always_allow / deny_once / always_deny`。
3. 移除临时的独立 `SocketClient` 发送方式，复用已连接客户端和统一请求队列，避免多个 TCP 连接造成事件与命令时序混乱。
4. 为每个 UI 订阅事件携带 `session_id/run_id` 过滤，重连后用历史和 replay 恢复，而非新建空会话覆盖当前任务。
5. 为此契约添加端到端测试：工具开始—结束、批准—继续、拒绝—恢复、断线—重连、事件回放五条关键链路。

### P1：补齐产品协议

以下是当时计划新增的 JSON-RPC/Pydantic 命令与事件；现行协议请查阅 [Wire Protocol](../reference/wire-protocol.md)：

| 类别 | 新命令 / 事件 | 目的 |
| --- | --- | --- |
| 会话 | `session.list`、`session.rename`、`session.archive`、`session.resume` | 左侧任务历史与恢复 |
| 工作区 | `workspace.open/list/recent`、`workspace.status` | 仓库身份、最近目录、Git 状态 |
| 文件 | `workspace.tree`、`file.read`、`file.search`、`file.changed` | 文件树与 diff 检查器 |
| 变更 | `change.list`、`change.diff`、`change.revert`、`change.applied` | 可审阅、可撤销的 Agent 改动 |
| 运行 | `run.cancel`、`run.get`、`run.replay`、`run.progress` | 停止、恢复和观测 |
| 计划 | `plan.updated`、`plan.item_updated` | 计划卡与进度 |
| 配置 | `settings.get/update`、`provider.status` | 设置中心与连接诊断 |

协议原则：所有列表接口支持稳定排序、分页/游标和时间戳；所有状态事件都含 `workspace_id/session_id/run_id` 中适用的关联键；每一种乐观 UI 都有服务端确认或可回滚路径。

### P2：客户端技术架构

推荐将产品级桌面端从 Tkinter 迁移到 **Tauri 2 + React + TypeScript**，Python daemon 保持为本地服务。Tauri 负责窗口、文件选择、系统通知和安全的系统桥接；React 负责可组合布局、虚拟化列表、Monaco diff、快捷键和可访问性；WebSocket/SSE 或现有 TCP 协议的受控桥接负责事件流。

保留 Textual TUI 作为 SSH/终端用户界面，但让桌面端成为主产品面。两端共享：Pydantic 协议、会话/运行领域模型、事件命名、设置格式与端到端场景测试。

建议分层：

```text
React 页面 / 组件
  ├── 状态层：WorkspaceStore、SessionStore、RunStore、PermissionStore
  ├── Client SDK：类型化 RPC、事件订阅、重连、事件去重、缓存
  └── Tauri bridge：窗口、目录选择、通知、打开外部编辑器
Python daemon
  ├── JSON-RPC 命令处理器 / EventBus
  ├── Session、Run、Workspace、Change 服务
  └── Agent / Tool / Permission / Trace（现有能力）
```

迁移期不建议“把 Tkinter 堆功能”。先完成 P0，再用独立 `desktop/` 前端包接入相同 daemon；旧 `sztu-desktop` 标记为 legacy，直到核心场景验收完成后移除。

## 7. 组件、状态与可访问性规范

### 组件清单

- `WorkspacePicker`、`SidebarTaskList`、`TaskRow`、`CommandPalette`
- `ConversationTimeline`、`UserPrompt`、`AgentNarrative`、`DeliveryCard`
- `PlanCard`、`RunTimeline`、`ToolCallCard`、`SubagentCard`
- `PermissionBar`、`ModeSelector`、`ContextMeter`
- `ChangeSummary`、`FileTree`、`DiffInspector`、`TestResultList`
- `SettingsDrawer`、`ProviderStatus`、`TraceViewer`

### 状态约束

- 运行状态：`idle → planning → running → waiting_permission → verifying → completed | failed | cancelled`。
- 对话、执行、变更三个流按 `session_id/run_id` 关联；只允许一个处于 active 的主 run，子 Agent 是该 run 的子节点。
- 流式 token 以 `run_id + sequence` 去重；页面离开不停止后台任务。
- 所有操作均反馈 loading、成功、失败；失败消息必须告诉用户“发生什么、是否影响结果、下一步能做什么”。

### 可访问性与国际化

- 所有图标按钮有可见 tooltip 与 `aria-label`；禁止只用颜色表达状态。
- 焦点指示清晰，模态框可 `Esc` 关闭且焦点返回触发点；审批默认焦点不能落在危险动作上。
- 中文为第一语言，同时预留 i18n key；时间、数字、快捷键和长路径做本地化与截断处理。
- 支持高对比度、缩放到 200%、减少动效；流式输出不应导致焦点跳动或读屏器重复播报。

## 9. 质量、测试与度量

### 测试策略

- 单元：领域 store、事件归并、权限决策映射、diff 解析、命令面板筛选。
- 契约：Python Pydantic 模型与 TypeScript 生成类型/契约测试，防止再次出现事件名漂移。
- 端到端：新任务、恢复历史、审批四种决策、工具失败重试、取消运行、断网重连、diff 审阅、回放。
- 视觉：关键页面在 1280×800、1440×900、1920×1080、窄窗口做截图回归。
- 性能：500 条任务列表和 10,000 条事件虚拟化；1000 token 流式输出时主线程不卡顿；冷启动目标小于 3 秒（不计模型连接）。

### 上线指标

- 任务成功完成率、权限拒绝后的恢复率、恢复会话成功率。
- 从输入目标到首个可见状态的时间、工具卡更新延迟、首次可审阅 diff 的时间。
- 每任务需要离开客户端的次数、审批误拒绝/误允许反馈、崩溃率。
- 7 日留存、单用户每周恢复会话次数、通过 diff 后继续迭代的比例。

## 10. 明确的优先级边界

首版不应包含云同步、多人协作、插件市场、内置完整 IDE、移动端或复杂的自定义主题系统。这些功能会稀释“可靠地完成一个本地代码任务”的主路径。

首版必须包含：工作区、可恢复会话、任务/计划、实时运行、可解释权限、文件变更/diff、测试结果、停止/重试、设置与诊断。先让用户能信任地委托并审阅一次完整编码任务，再扩展生态能力。
